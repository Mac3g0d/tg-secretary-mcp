# Архитектура

Документ описывает, из чего состоит `tg-secretary`, как данные попадают в архив и как их читают.
Связанные документы: [настройка](configuration.md), [инструменты MCP](mcp-tools.md), [веб-интерфейс](web-ui.md).

## Компоненты и поток данных

```
 Telegram Bot API
       │  getUpdates (long polling, таймаут 50 с)
       ▼
 ┌───────────┐  запись   ┌──────────────────────────┐  чтение   ┌─────────────┐
 │ collector │ ────────▶ │ SQLite: chats, messages, │ ◀──────── │ mcpserver   │ ◀── агент
 │ (бот)     │           │ messages_fts, cursors,   │           └─────────────┘
 └───────────┘           │ business_connections,    │  чтение   ┌─────────────┐
       ▲                 │ meta                     │ ◀──────── │ web         │ ◀── браузер
       │ sendMessage     └──────────────────────────┘           └─────────────┘
       └──── инструмент send_message (только при TG_ALLOW_SEND=true)
```

Один процесс `tg-secretary serve` содержит все части: сборщик, MCP-сервер и веб-интерфейс.
Те же части можно запускать раздельно (см. [режимы запуска](configuration.md#режимы-запуска)).

## Пакеты

| Пакет | Ответственность |
| --- | --- |
| `cmd/tg-secretary` | Точка входа: разбор команды и флагов, загрузка конфигурации, запуск компонентов, обработка SIGINT/SIGTERM |
| `internal/config` | Чтение переменных окружения и `.env`, проверка значений |
| `internal/telegram` | Минимальный клиент Bot API: `getMe`, `getUpdates`, `sendMessage`, типы обновлений. Убирает токен из текста сетевых ошибок |
| `internal/collector` | Цикл long polling, преобразование обновлений в записи, хранение смещения обновлений |
| `internal/store` | Схема SQLite, запросы, разрешение ссылки на чат, курсоры |
| `internal/mcpserver` | Инструменты MCP поверх `store` (и клиента Telegram для отправки) |
| `internal/web` | Веб-интерфейс: HTML-шаблоны и стили вшиты в бинарник |
| `internal/httpserver` | HTTP-сервер: маршруты `/mcp`, `/`, `/healthz` и проверка токена |
| `internal/app` | Собирает компоненты (бот, HTTP, stdio) и управляет их запуском и остановкой |

Первый компонент, который завершился или упал, останавливает весь процесс.
По SIGINT/SIGTERM HTTP-сервер получает 5 секунд на завершение запросов.

## Схема SQLite

База открывается драйвером `modernc.org/sqlite` (чистый Go, без cgo, FTS5 входит в состав).
При открытии создаются каталог (права `0700`) и недостающие таблицы (`CREATE ... IF NOT EXISTS`),
файлу базы выставляются права `0600`. Затем применяются миграции: номер версии схемы хранится
в `PRAGMA user_version`, недостающие шаги выполняются в одной транзакции под блокировкой записи,
так что два процесса, открывающие базу одновременно, не применят шаг дважды.
База от более новой версии программы не открывается. Версия 1 (после v0.1.0) добавила в `messages`
столбцы `forward_from`, `forward_from_username`, `forward_date` и `imported`.
Версия 2 добавила таблицу `chat_photos`.

Параметры соединения: `journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=1`, `synchronous=NORMAL`.

### chats

| Колонка | Тип | Описание |
| --- | --- | --- |
| `id` | INTEGER, PK | ID чата в Telegram (у групп и каналов отрицательный) |
| `type` | TEXT | `private`, `group`, `supergroup` или `channel` |
| `title` | TEXT | Название чата; для личных чатов имя собеседника |
| `username` | TEXT | `@username` без `@`, если есть |
| `business_connection_id` | TEXT | Бизнес-подключение, через которое виден чат; пустое значение при обновлении не затирает сохранённое |
| `updated_at` | INTEGER | Unix-время последнего обновления записи |

### messages

| Колонка | Тип | Описание |
| --- | --- | --- |
| `pk` | INTEGER, PK AUTOINCREMENT | Локальный порядковый номер вставки |
| `chat_id` | INTEGER | Ссылка на `chats.id` |
| `id` | INTEGER | `message_id` из Telegram; уникален только внутри чата |
| `date` | INTEGER | Время сообщения (Unix) |
| `sender_id` | INTEGER | ID пользователя или чата-отправителя; 0, если неизвестен |
| `sender_name` | TEXT | Отображаемое имя отправителя |
| `sender_username` | TEXT | `username` отправителя без `@` |
| `text` | TEXT | Текст сообщения или подпись к вложению |
| `media_type` | TEXT | Тип вложения; пусто для обычного текста |
| `reply_to_id` | INTEGER | `message_id` сообщения, на которое это ответ; 0, если не ответ |
| `is_outgoing` | INTEGER | 1, если написано ботом или владельцем бизнес-аккаунта |
| `edited_at` | INTEGER | Время последней правки; 0, если не правилось |
| `deleted_at` | INTEGER | Время, когда бот узнал об удалении; 0, если не удалено |
| `saved_at` | INTEGER | Время первой записи в архив |
| `forward_from` | TEXT | Имя автора оригинала у пересланного сообщения, иначе пусто |
| `forward_from_username` | TEXT | `username` автора оригинала, если есть |
| `forward_date` | INTEGER | Время оригинала у пересланного сообщения; 0, если не переслано или неизвестно |
| `imported` | INTEGER | 1, если сообщение загружено из экспорта, а не получено ботом |

Ограничение `UNIQUE (chat_id, id)`. Индексы: `messages_chat_date (chat_id, date)` и `messages_date (date)`.

Про `pk` и `id`:

- `id` (в API и интерфейсе `message_id`) задаёт Telegram, он повторяется в разных чатах.
  Именно его принимает `get_message_context` и именно он виден агентам.
- `pk` присваивает база в порядке вставки. По нему работает курсор «новых сообщений», и он никогда не
  переиспользуется (`AUTOINCREMENT`). Наружу `pk` не отдаётся.

### messages_fts

Виртуальная таблица FTS5 с внешним содержимым:

```sql
CREATE VIRTUAL TABLE messages_fts USING fts5 (
    text, sender_name,
    content='messages', content_rowid='pk',
    tokenize='unicode61 remove_diacritics 2'
);
```

Данные в индекс не дублируются: он ссылается на `messages` по `pk`. Синхронизацию обеспечивают три триггера:

- `messages_ai` после вставки добавляет строку в индекс;
- `messages_ad` после удаления строки убирает её из индекса;
- `messages_au` после обновления `text` или `sender_name` убирает старую версию и добавляет новую.

Пометка об удалении (`deleted_at`) индекс не меняет: удалённые сообщения отфильтровываются в запросе.
Токенизатор `unicode61` сравнивает слова без учёта регистра (в том числе для кириллицы)
и игнорирует диакритику. Как запрос превращается в выражение FTS5, описано
в разделе [синтаксис поиска](mcp-tools.md#синтаксис-поиска).

### business_connections

| Колонка | Тип | Описание |
| --- | --- | --- |
| `id` | TEXT, PK | ID бизнес-подключения |
| `user_id` | INTEGER | ID пользователя, которому принадлежит подключение |
| `enabled` | INTEGER | Включено ли подключение |

### chat_photos

Аватарки чатов. Строка есть у каждого чата, который бот уже проверял, в том числе у чатов без фото.

| Столбец | Тип | Описание |
| --- | --- | --- |
| `chat_id` | INTEGER PK | ID чата |
| `unique_id` | TEXT | Идентификатор версии фото (`small_file_unique_id`); пусто, если фото нет |
| `content_type` | TEXT | Тип изображения, например `image/jpeg` |
| `data` | BLOB | Само изображение 160×160; NULL, если фото нет или оно недоступно боту |
| `checked_at` | INTEGER | Когда фото проверялось в последний раз |

Загрузкой занимается фоновая задача сборщика: она просыпается раз в минуту и после каждой пачки обновлений,
берёт до 20 чатов без проверки за последние сутки и сверяет `unique_id` с тем, что отдаёт Telegram.

### cursors

| Колонка | Тип | Описание |
| --- | --- | --- |
| `name` | TEXT, PK | Имя читателя (`consumer`) |
| `last_pk` | INTEGER | `pk` последнего подтверждённого сообщения |
| `updated_at` | INTEGER | Время последнего сдвига |

### meta

Таблица ключ-значение. Ключи ведёт сборщик:

| Ключ | Значение |
| --- | --- |
| `update_offset` | Смещение для следующего `getUpdates` |
| `bot_username` | Имя бота, определённое через `getMe` при старте |
| `last_update_at` | Unix-время, когда бот последний раз получил непустую порцию обновлений |

## Как сборщик обрабатывает обновления

Бот запрашивает такие типы обновлений: `message`, `edited_message`, `channel_post`,
`edited_channel_post`, `business_connection`, `business_message`, `edited_business_message`,
`deleted_business_messages`.

**Новые сообщения.** Для каждого сообщения сначала обновляется запись чата (`chats`), затем
вставляется строка в `messages`. Отправителем считается `sender_chat` (посты каналов и анонимные админы),
а если его нет, то `from`. Служебные сообщения (вступления, закрепления и т. п.), в которых нет ни текста,
ни вложения, пропускаются. Тип вложения определяется по полям `photo`, `video`, `video_note`, `voice`,
`audio`, `animation`, `document`, `sticker`, `poll`, `location`, `contact`; сами файлы не загружаются.

**Правки.** Повторное сообщение с тем же `(chat_id, id)` не создаёт новой строки: обновляются `text`,
`media_type`, `edited_at`, `sender_name` и `sender_username`. Дата, `pk`, признак `is_outgoing` и `reply_to_id`
остаются прежними. Триггер `messages_au` переиндексирует текст. Если правка пришла для сообщения,
которого в архиве не было (бот ещё не работал), оно просто добавится с отметкой о правке.

**Удаления.** Telegram сообщает боту об удалении только в бизнес-чатах (`deleted_business_messages`).
Сообщения получают `deleted_at`, но остаются в базе. По умолчанию инструменты и веб-интерфейс их скрывают;
показать их можно параметром `include_deleted` (MCP) или флажком «удалённые» (веб).
В обычных группах и каналах удаления не видны, такие сообщения остаются в архиве как есть.

**Бизнес-подключения.** Обновление `business_connection` записывает, какому пользователю принадлежит
подключение. Сообщения `business_message` и `edited_business_message` сохраняют `business_connection_id`
в записи чата, и `send_message` использует его, чтобы отвечать от имени владельца аккаунта.

**Определение исходящих (`is_outgoing`).** Сообщение считается исходящим, если:

- в обычном чате его автор совпадает с самим ботом;
- в бизнес-чате его автор совпадает с владельцем подключения (`business_connections.user_id`).
  Пока бот не получил обновление `business_connection`, владелец неизвестен и такие сообщения
  считаются входящими.

Бот не получает собственные сообщения как обновления. Поэтому `send_message` сам записывает отправленное
сообщение в архив с признаком исходящего.

**Фильтр чатов.** Если задан `TG_ALLOWED_CHATS`, сообщения из остальных чатов не сохраняются
(и запись чата для них не создаётся).

**Ошибки записи.** Если обновление не удалось записать, ошибка пишется в лог, а обработка идёт дальше:
смещение всё равно сдвигается, и это обновление пропускается.

## Смещение обновлений

Сборщик хранит в `meta.update_offset` значение «`update_id` последнего обработанного обновления плюс 1».
После каждой непустой порции обновлений смещение записывается в базу. После перезапуска бот продолжает с него,
поэтому ничего не пропускается и не обрабатывается повторно. Если процесс упадёт посреди порции, она придёт
снова; повторная запись идемпотентна благодаря `UNIQUE (chat_id, id)`.

Обработка ошибок опроса:

- `401` от Bot API (неверный токен) завершает бота с ошибкой;
- ошибка `getMe` при старте завершает процесс (под systemd его перезапустит `Restart=on-failure`);
- остальные ошибки, включая `409` («другой процесс уже опрашивает этот токен»), повторяются
  с задержкой от 1 секунды, удваиваемой до 1 минуты; если сервер указал `retry_after`, ждут не меньше этого.

## Курсор новых сообщений

Инструмент `get_new_messages` ведёт позицию по имени `consumer` в таблице `cursors`:

- Для неизвестного `consumer` возвращаются сообщения за последние 24 часа.
- Для известного возвращаются сообщения с `pk` больше сохранённого, в порядке `pk` (старые первыми).
- По умолчанию возвращаются только входящие и неудалённые сообщения (`include_outgoing=false`).
- Сообщения, загруженные импортом (`imported=1`), в ленту не попадают никогда: это история, а не новости.
- Максимальное значение `pk` читается до запроса, чтобы сообщение, пришедшее в промежутке, не было пропущено.
- После ответа позиция сдвигается (если не задан `peek`): на `pk` последнего возвращённого сообщения,
  если `has_more=true`, иначе на максимальный `pk` в базе. Так отфильтрованные строки (исходящие, удалённые)
  не возвращаются при следующем вызове.
- Правка уже прочитанного сообщения не возвращает его снова: у правки тот же `pk`.
- Позиции разных `consumer` независимы. Один и тот же `consumer` у двух агентов делит одну позицию.

## Модель конкурентности

- Опрашивать `getUpdates` с одним токеном может только один процесс. Бот запускается либо в `serve`, либо в `bot`.
  Второй опрашивающий процесс получит от Telegram ошибку `409` и будет повторять попытки.
- База открыта в режиме WAL: читатели не блокируют писателя. Поэтому `tg-secretary bot` и несколько процессов
  `tg-secretary stdio` (например, по одному на агента) могут одновременно работать с одним файлом.
  Запись остаётся единственной; при занятой базе запрос ждёт до 5 секунд (`busy_timeout`).
- Все процессы должны указывать на один и тот же файл. Относительный `TG_DB_PATH` считается от рабочей
  директории процесса, поэтому для нескольких процессов задавайте абсолютный путь.
- Пул соединений `database/sql` делает `Store` безопасным для одновременного использования из сборщика,
  MCP-обработчиков и веб-запросов в одном процессе.
- Вместе с основным файлом SQLite создаёт `-wal` и `-shm`. Учитывайте это при [резервном копировании](deployment.md#резервные-копии).
